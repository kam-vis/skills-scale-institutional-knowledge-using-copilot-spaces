# OctoAcme — Project Management Overview

OctoAcme runs projects with a lightweight, iterative approach centered on clear outcomes and measurable success. Work starts with a short Project One‑pager that states the problem, objective, success metrics, stakeholders, and a high‑level timeline; teams only move into planning when success criteria, priority, and resource availability are confirmed. The lifecycle is intentionally simple: Initiation → Planning → Execution → Release → Close & Retrospective, and key artifacts (one‑pager, roadmap, backlog, risk register, and Definition of Done) are kept in the repository so work and decisions remain discoverable.

Day‑to‑day execution uses a visible project board (Backlog, Ready, In Progress, In Review, QA, Done) to manage flow. Planning breaks work into small, shippable increments with clear acceptance criteria and estimates. Pull request discipline helps keep changes reviewable and safe: aim for small PRs, include the related issue and acceptance criteria in the description, run CI (tests, lint, and security scans) before requesting review, and follow the team’s approval policy before merging. Cross‑team dependencies and risks are tracked in a simple risk register and escalated during regular syncs.

Roles and responsibilities are explicit so ownership is clear. Product Managers define outcomes and success metrics; Project Managers coordinate delivery, timelines, risks, and stakeholder communications; Developers implement features, write tests, and participate in reviews; QA validates acceptance criteria and performs manual checks where needed. These persona definitions help keep expectations aligned and are also used as prompts for exercises and onboarding materials.

Communication and quality assurance are embedded into the cadence: daily standups surface progress and blockers, weekly delivery syncs focus on progress and risks, demos/reviews close iterations, and monthly stakeholder updates keep broader audiences aligned. QA expectations include unit and integration tests for new logic, end‑to‑end smoke tests for critical flows, CI‑based security scanning, and a rollback/mitigation plan for releases. Retrospectives convert learnings into tracked action items that feed back into the backlog for continuous improvement.
